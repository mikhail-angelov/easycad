# Адресуемые грани EasyCAD: форматы и открытые компоненты

Дата проверки первичных источников: 6 сентября 2026. Это исследовательское приложение, не описание уже внедрённой функции. Новые библиотеки не устанавливались, внешний код не запускался. Совместимость конкретных версий и влияние на скорость требуют локальной проверки.

## Вывод

Пользователь понял рекомендацию правильно: буква A должна обозначать выбранную **CAD-грань**, а не один треугольник STL. Нажатие на поверхность, её подсветка и короткая ссылка в сообщении дают генератору гораздо более точное указание, чем «боковая сторона». Это применимо к коробкам, кронштейнам, корпусам и другим деталям, не только к резьбе.

Рекомендуемый первый вариант: оставить STL для скачивания, передавать в браузер сетку с соответствием `треугольники → CAD-грань`, а в запрос — серверно проверяемые `revision_id + face_id`. Начать с выбора любых отображаемых граней, но гарантированное размещение эскиза/надписи ограничить плоскими гранями. Это инженерная рекомендация, а не измеренный прирост качества.

## Что дают форматы

| Представление | Что полезно для задачи | Ограничение |
| --- | --- | --- |
| STL | Скачивание и печать, существующий просмотрщик | Это сетка, а не адресуемые поверхности исходного CAD |
| STEP / BREP | Точная геометрия и топология для CAD-операций на сервере | Для браузерного показа всё равно нужна тесселяция; формат сам не создаёт неизменные имена граней |
| glTF / GLB | Веб-сцена, сетки, материалы, переносимое отображение | Связь с исходной CAD-гранью требует явных метаданных и контракта |
| Сетка + JSON-метаданные | Прямой путь от клика до серверной грани без замены CAD-движка | EasyCAD отвечает за версию модели, диапазоны треугольников и жизненный цикл выбора |

CadQuery официально поддерживает STL, STEP и glTF; последний экспортируется через Assembly. Поддержка STEP-метаданных включает имена, цвета и слои подфигур через `Assembly.addSubshape()`. Документация отдельно предупреждает: экспортируемые форматы не сохраняют параметрическую программу CadQuery; исходный Python остаётся её носителем. [CadQuery: import/export](https://cadquery.readthedocs.io/en/stable/importexport.html).

В glTF есть mesh primitives и поле `extras` для данных приложения. Следовательно, туда можно вложить собственные ссылки на грани, но стандарт не определяет их CAD-смысл или сохранность после перестроения. Это вывод из состава формата, а не обещание, что штатный экспорт CadQuery уже отдаёт нужный EasyCAD контракт. [Спецификация glTF 2.0](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html).

## Как получить соответствие без восстановления граней из STL

В исходниках CadQuery **v2.8.0** `Shape.tessellate()` последовательно перебирает `Faces()`, читает их триангуляции, учитывает преобразование и ориентацию и объединяет вершины/треугольники. Возвращаемая пара массивов сама не содержит границ диапазонов CAD-граней. Практический вариант — тесселировать каждую грань отдельно и сохранить её диапазон при объединении. Это предложение на основе доступного API, которое нужно проверить на установленной версии. [Исходник v2.8.0](https://github.com/CadQuery/cadquery/blob/v2.8.0/cadquery/occ_impl/shapes.py#L1480).

`Raycaster` three.js возвращает `faceIndex` и точку попадания. Здесь face означает треугольную грань визуальной сетки: соответствие CAD-граням должен дать сервер. Поэтому индекс попадания можно преобразовать в `face_id`, не отправляя изображение в vision-модель. [Three.js: Raycaster](https://threejs.org/docs/pages/Raycaster.html).

`BufferGeometry` поддерживает индексы, атрибуты и группы. Каждая группа создаёт отдельный draw call, поэтому назначать отдельный материал каждой из тысяч CAD-граней не обязательно: для первого варианта достаточно общей сетки и отдельной подсветки выбранного диапазона. Последнее — предлагаемая оптимизация интерфейса. [Three.js: BufferGeometry](https://threejs.org/docs/pages/BufferGeometry.html).

Не следует сопоставлять отдельно экспортированный STL и отдельно созданный список граней только по предполагаемому порядку треугольников. Надёжный контракт формируется в том проходе, который строит именно отображаемую сетку; альтернативный путь через STL требует проверки и сохранения точного соответствия его треугольников.

## Открытые компоненты, которые стоит проверить

- **ocp-tessellate** превращает OCP-геометрию в JSON-friendly данные для three-cad-viewer. README заявляет совместимость с CadQuery 2.x и OCP 7.8/7.9. Лицензия Apache-2.0 проверена в LICENSE. Это кандидат на готовую серверную тесселяцию, но заявленная совместимость ещё не доказывает работу конкретного закреплённого релиза в EasyCAD. [Репозиторий](https://github.com/bernhard-42/ocp-tessellate), [лицензия](https://github.com/bernhard-42/ocp-tessellate/blob/main/LICENSE).
- **three-cad-viewer** — готовый viewer на three.js; документация описывает фильтры выбора vertex/edge/face/solid. Лицензия MIT проверена в LICENSE. Полная замена текущего viewer имеет смысл, если нужны также CAD-рёбра, измерения и несколько режимов выбора; ради одной подсветки её цена может быть избыточной. Это оценка объёма интеграции, а не замер. [Репозиторий](https://github.com/bernhard-42/three-cad-viewer), [лицензия](https://github.com/bernhard-42/three-cad-viewer/blob/master/LICENSE).
- Формат three-cad-viewer уже содержит `triangles_per_face`, `face_types`, `segments_per_edge`, `obj_vertices`. Можно использовать его как проверенный ориентир контракта, даже сохранив существующий viewer. `obj_vertices` — исходные топологические вершины; множество вершин триангуляции не равно множеству CAD-вершин. [Описание формата](https://github.com/bernhard-42/three-cad-viewer/blob/master/Data%20Format.md).
- **jupyter-cadquery** ориентирован на отображение CadQuery в JupyterLab. Для FastAPI/Preact-приложения полезнее проверять его нижележащие компоненты, чем внедрять notebook-интеграцию. [Первичный репозиторий](https://github.com/bernhard-42/jupyter-cadquery).

Ни скачивания, ни число звёзд здесь не считаются доказательством качества. Сравнение «небольшое расширение существующего viewer» и «ocp-tessellate + three-cad-viewer» следует делать на одной коробке, цилиндре, детали со скруглениями и многотельной модели.

## Буква A не должна быть вечным именем

После выреза одна грань может разделиться, несколько граней — объединиться, грань — исчезнуть. OCCT для этого хранит отношения старых и новых фигур, а `TNaming_Selector` использует отдельный механизм идентификации и обновления. Простой порядковый номер не заменяет такой механизм. [OCCT: эволюция топологии](https://dev.opencascade.org/doc/refman/html/_t_naming___evolution_8hxx.html), [OCCT: TNaming_Selector](https://dev.opencascade.org/doc/refman/html/class_t_naming___selector.html).

В CadQuery 2.8 есть **экспериментальная поддержка истории**. Поэтому утверждение «в CadQuery вообще нет истории» было бы неверным. Но наличие API истории не доказывает устойчивую идентичность граней между произвольными версиями Python-кода, заново сгенерированного LLM. [Анонс CadQuery 2.8](https://github.com/CadQuery/cadquery/discussions/2051).

Предлагаемый контракт первого этапа:

1. Сервер выдаёт токен именно полученного снимка геометрии и локальные номера граней; буквы — только человекочитаемые метки.
2. Запрос с выбором несёт токен снимка и номер, сервер проверяет их принадлежность текущей модели пользователя. Центр, нормаль и тип берутся из серверных данных, не на веру из браузера.
3. При успешном изменении геометрии выбор сбрасывается, метки относятся уже к новой ревизии. Устаревшая ссылка явно отклоняется.
4. Если сервер не сохраняет BREP снимка и заново выполняет код, одного hash исходника недостаточно для гарантии той же геометрии: возможны случайные значения и смена окружения. Нужно сверять результат либо работать с сохранённым снимком. Нельзя молча считать порядковую грань той же самой.

## «В центре грани» и гравировка ABC

`Face.Center()` в CadQuery v2.8.0 вычисляет центр масс поверхности. Из геометрии следует: у кольцевой грани он может находиться в отверстии, у боковой цилиндрической — на оси, вне самой поверхности. Даже средина UV-диапазона не гарантирует попадание внутрь обрезанной грани с отверстиями. Значит, точка для подписи и место операции требуют проверки принадлежности; для первой версии практичнее клик по поверхности плюс отдельно показанное правило центрирования. [Реализация Face.Center/normalAt](https://github.com/CadQuery/cadquery/blob/v2.8.0/cadquery/occ_impl/shapes.py#L3245).

CadQuery `Workplane.text()` умеет создавать объёмный текст и вычитать его, позволяет задавать размер, направление/глубину, шрифт и выравнивание. Это подходящая операция для плоской стороны коробки, но не автоматическая развёртка на произвольной криволинейной поверхности. [CadQuery: Workplane.text](https://cadquery.readthedocs.io/en/stable/classreference.html#cadquery.Workplane.text).

Для сценария «ABC в центре A» нужны ещё размер букв, глубина и ориентация чтения. Их можно предложить как видимые допущения и дать изменить. Проверки результата: текст действительно пересёк целевую деталь, уменьшил её объём, расположен на нужной стороне и не прорезал стенку насквозь без запроса. Одной красивой подсветки для этих гарантий недостаточно.

## Самый маленький полезный эксперимент

Выбор и маркировка грани → прикрепление ссылки к чату → выполнение одной адресной правки на плоской грани → проверка результата. Проверить не только коробку: цилиндр для непрерывной кривой грани, кольцо для центра в отверстии, две разнесённые детали для принадлежности тела, скруглённый корпус для большого числа граней. Отдельный отрицательный сценарий — отправить старую ссылку после перестроения.

На первом этапе не нужны vision-модель, распознавание граней по STL, постоянные идентификаторы на всю историю и одновременная маркировка всех вершин. Выбор граней снижает неоднозначность места правки, но улучшение итогового качества генератора ещё следует измерить на адресных запросах.
